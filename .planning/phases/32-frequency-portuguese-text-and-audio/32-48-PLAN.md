# Phase 32 Plan 48: Disposable DB Reset And Migration Rehearsal

## Objective
Use the user's explicit `Wipe Current DB` authorization to reset only the `public` schema of the exact disposable/test `.env` PostgreSQL target that blocked Plan 32-47, then run Alembic `upgrade head` and validate current-head runtime readiness without granting production authority.

## Context
- Plan 32-47 rewrote the production migration goal into a disposable/test rehearsal after the user confirmed the `.env` target is disposable/test and recreatable.
- Plan 32-47 stopped before migration because preflight found application tables but no Alembic revision metadata, which would make Alembic-from-base collide with legacy tables.
- The user then selected `Wipe Current DB`, explicitly authorizing destructive reset of that disposable target.
- `.planning/SPEC.md` and `.planning/ROADMAP.md` still keep Phase 32 open because production DB, voice profile/audio, production-scale generation, review/remediation, export, release, and delivery evidence are absent.

## Requirements Covered
- KFREQ-01, GLEX-01, GLEX-02, GPRO-01, KAUD-01, GAUD-01

## Must-Haves
1. The destructive reset is bound to the same sanitized target hashes recorded by Plan 32-47.
2. The reset touches only the disposable target's `public` schema and records row-count-only data loss evidence.
3. Alembic reaches unique head `20260828_19` after reset.
4. Post-validation proves zero application rows, Phase 32 evidence columns, Phase 33 current-head DDL acknowledgment, runtime provisioning no-op, and no secret leakage.

## Anti-Goals
- No important/production database mutation, production readiness claim, backup/restore waiver for production, or promotion of disposable evidence into production authority.
- No provider, generation, translation, Azure catalog, audio, review, export, release, delivery, commit, PR, or Phase 32 closure.
- No raw locator, secret, private path, row content, prompt, completion, provider payload, Korean generated text, or Portuguese generated text in evidence.
- No Alembic stamp, downgrade, manual schema reconciliation, data seeding, role mutation, `.env` mutation, or non-public schema deletion.

## Hard Boundaries
- Use `.env` only through `uv run --env-file .env` and do not print environment values.
- Destructive SQL is fixed and limited to `DROP SCHEMA IF EXISTS public CASCADE` and `CREATE SCHEMA public` after exact hash guard passes.
- If `public` reset succeeds but Alembic fails, do not repair manually; record sanitized failure and stop.
- Phase 33 DDL is allowed only as current Alembic head schema, not as Phase 33 workflow/data execution.

## Evidence Contract
- `disposable-database-reset-authorization.md` records `user_choice=Wipe Current DB`, `classification=disposable/test`, `destructive_reset_authorized=true`, `production_authority=false`, and a non-secret link to Plan 32-47 hashes.
- `tools/disposable_database_reset_rehearsal.py` contains the auditable fixed-SQL reset helper and is part of the reviewed plan surface.
- `disposable-database-reset-preflight.json` proves exact target hash equality with Plan 32-47, writable primary state, sole head `20260828_19`, absence of application tables outside `public`, absence of unexpected public tables, and complete allowed-public-table pre-reset row counts.
- `disposable-database-reset-result.json` records the fixed reset statements by stable identifiers, pre/post schema hashes, destroyed row counts by table name, and `manual_sql_used=false` except for `fixed_public_schema_reset=true`.
- `disposable-database-after-reset-migration-result.json` records Alembic `upgrade head`, before/after revision, schema hashes, and zero provider/content/audio/export side effects.
- If reset or migration fails, the relevant result artifact records `status`, `failure_stage`, `blocked_reason`, `public_schema_exists_after_failure`, zero provider/content/audio/export deltas, `production_authority=false`, and `raw_secret_persisted=false` without raw exception text.
- `disposable-database-after-reset-validation.json` records current revision `20260828_19`, Phase 32 columns present, Phase 33 head acknowledged, runtime provisioning no-op at head, all application row counts zero, and `production_ready=false`.
- Final verification must scan all Plan 32-48 artifacts and summary for raw DB URLs, URL-like Postgres locators, private absolute paths, and exact non-generic DB URL components.

## Common Pitfalls
- Accidentally treating the destructive reset as a production-safe migration pattern.
- Widening from `public` schema reset to database/role/non-public-schema deletion.
- Continuing after target hash drift because the `.env` variable still exists.
- Running Alembic stamp or manual repair to hide an incomplete migration.
- Claiming content/audio/export readiness from schema-only evidence.

## Stop-And-Challenge
- Stop if target locator hash or database identity hash differs from Plan 32-47 preflight.
- Stop if the database is not PostgreSQL, is read-only, is in recovery, lacks reset privileges, or contains app tables outside `public`.
- Stop if reset leaves `public` absent and cannot recreate it with the same connection user.
- Stop if Alembic has multiple heads or head is not `20260828_19`.
- Stop if any artifact would need to disclose a secret, raw locator, row content, provider payload, prompt, completion, generated text, or private path.

## Approval Gates
- Current-session destructive approval is present from the user's `Wipe Current DB` answer.
- Re-ask before executing this plan in any later session, if `.env` changes, or if target hash/identity does not match Plan 32-47.
- Production/important DB migration still requires a separate production-safe plan with backup, restore, and rollback evidence.
